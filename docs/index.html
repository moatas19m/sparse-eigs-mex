The opening

Why there is room to win at all

eigs is not slow because it is written in MATLAB — underneath it is ARPACK, compiled Fortran. It is slow here because of three specific decisions, each of which I can reverse.

For the smallest-magnitude case it performs a shift-invert: factorize A, then run Lanczos on A⁻¹. To factorize, it calls MATLAB's lu — which is UMFPACK unsymmetric multifrontal LU, even when the matrix is symmetric positive definite. It orders with AMD rather than nested dissection. And on R2017a and older, ARPACK's reverse-communication interface hands control back to the MATLAB interpreter once per matrix-vector product.

So eigs throws away symmetry, throws away positive-definiteness, uses a weaker ordering for three-dimensional problems, and pays an interpreter round trip on every iteration. It also never inspects the sparsity pattern for reducibility, disconnection, or bandedness.

Evidence

What the two factorization paths actually cost

I wrote a standalone probe timing both paths on the same matrix: a 3-D 7-point Laplacian, which produces realistic finite-element fill. Not a benchmark of eigs itself — a measurement of the component that dominates its runtime.

The flop ratio of about 4× is roughly half from exploiting symmetry and half from METIS nested dissection beating AMD on a 3-D problem. The remaining wall-clock gain is supernodal BLAS-3 efficiency: CHOLMOD assembles large dense supernodes that Accelerate can drive at near-peak rate, where UMFPACK's frontal matrices are smaller and less efficient.

A correction to my own first measurement

My initial probe reported a fill ratio of 39× and a flop ratio of 173×. Those were wrong — I had read UMFPACK's *_ESTIMATE fields, which are symbolic upper bounds, against CHOLMOD's actuals. Reading the post-factorization actuals gives the honest 2.87× and 4.03× above. The timings were measured directly and were never affected. Worth stating plainly, because an unchallenged 173× would not have survived contact with a referee.

My earlier estimate was wrong by an order of magnitude in n

Before writing the solver I modelled the speedup from component timings and predicted 6.0–8.2×, with the risk zone below n ≈ 5,000. The finished solver gives 5.6× at n = 64,000, and the true crossover is near n ≈ 58,000 — about ten times higher than I claimed. The model priced the triangular solves but not the iteration around them: orthogonalisation, residual checks and restart cost about 13% of the iteration phase, and the model gave the factorization advantage more weight than it earns end to end.

Where the time actually goes at n = 64,000: analysis 0.31 s, factorization 0.19 s, iteration 1.00 s. Within that iteration phase the solves are 86% of the cost and the surrounding algorithm is 13% — so the implementation is not leaving much on the table. 74 operator applications, 6 restarts, maximum residual 1.8 × 10⁻¹⁴.

The shortfall

Why small matrices miss, and why tuning will not save them

Below n ≈ 58,000 the solver lands at 3.6–3.9×. I checked whether this was an artifact of my own choices before concluding it was structural, and it is not an artifact.

The obvious suspect was the fill-reducing ordering. Comparing AMD against METIS end to end: at n = 8,000 AMD wins (0.055 s vs 0.092 s) because METIS's analysis phase dominates everything else; by n = 15,625 METIS wins (0.199 s vs 0.231 s); at n = 64,000 it wins again (1.50 s vs 1.62 s). The crossover sits between 8,000 and 15,625, so I moved the threshold from 20,000 to 12,000 — worth about 14% at n = 15,625, and nowhere near enough to turn 3.7× into 5×.

The real cause is structural: on smaller problems UMFPACK's LU simply produces less fill, so the advantage of exploiting symmetry and using nested dissection shrinks with it. There is no tuning knob for that. Closing the gap at small n would need a different attack — eliminating eigs' per-iteration interpreter overhead, which I cannot measure without MATLAB, or the dense LAPACK path, which only reaches so far up.

One caveat that runs in the other direction, stated without claiming credit for it: this comparison charges eigs nothing for ARPACK's reverse communication, which on R2017a re-enters the MATLAB interpreter once per matrix-vector product. That overhead is proportionally largest exactly where I am weakest. It may narrow the gap at small n. I have not measured it and am not counting it.

The semi-definite case

Where eigs is not just slower — it is wrong

The requirement notes that the matrices may be only semi-definite. That is the sharpest part of the requirement: if A is singular, shift-inverting at σ = 0 asks the code to invert a singular matrix. I probed it directly on a Neumann Laplacian — row sums zero, so it is positive semi-definite with rank n−1 and a one-dimensional null space.

n = 27,000, rank 26,999

cholmod_l_factorize  →  status = CHOLMOD_NOT_POSDEF,  L->minor = 26999 of 27000
umfpack_dl_numeric   →  status = UMFPACK_OK,           rcond   = 9.075e-13

CHOLMOD detects the rank deficiency exactly

It reports the precise column at which factorization broke down — L->minor = 26999, exactly the one-dimensional null space. That is a free, reliable rank signal I can act on.

UMFPACK reports success on a singular matrix

It returns OK with a reciprocal condition estimate of 9 × 10⁻¹³. This is the path eigs takes — it proceeds on a numerically meaningless factorization. So on semi-definite input, the proposed function is not merely faster; it is more correct. That may matter more to you than the timing.

How I handle it

Estimate ‖A‖₁, then factorize A + δI with δ escalating geometrically from ‖A‖₁·√ε. The probe confirms this succeeds at every δ tested, down to 1.2 × 10⁻¹¹. Run Lanczos on (A+δI)⁻¹ — then discard the shifted eigenvalue estimates entirely and recompute each λ as a Rayleigh quotient vᵀAv / vᵀv against the original A, reporting residuals ‖Av − λv‖ against the original A as well.

The consequence is the point: δ affects only the rate of convergence, never the accuracy of the answer.

One further trap. A semi-definite matrix has λ = 0 with multiplicity equal to its nullity, and plain Lanczos is notorious for missing repeated eigenvalues, because a Krylov space built from one starting vector contains only a single direction from each eigenspace. The implemented fix is full reorthogonalisation plus random re-injection on breakdown: when the recurrence exhausts an invariant subspace, a fresh vector orthogonal to everything already found is injected, which brings the remaining copies into reach.

It works. On the singular Neumann Laplacian the solver returns λ₀ = −4.3 × 10⁻¹⁹ with a null vector constant to 1.2 × 10⁻¹⁶; on the Dirichlet Laplacian it recovers all three copies of a genuine multiplicity-3 eigenvalue with eigenvectors mutually orthogonal to 3 × 10⁻¹⁶.

Your second requirement

Exploiting the nonzero structure

Every test below is O(nnz) and runs before any numerical work. eigs performs none of them. These are where order-of-magnitude wins live, as opposed to the steady 5–8× from the factorization.

Not needed for SPD, but it is how the design keeps the "works for any matrix" promise if the symmetry assumption is ever relaxed.

What exists now

The solver, and how it is validated

The numerical core is plain C with no MATLAB dependency — it takes raw CSC arrays and returns eigenpairs. That is deliberate: it means the mathematics can be compiled, run and validated on a machine with no MATLAB on it, and the MEX file is reduced to a thin gateway. It builds clean under both Apple clang 17 and GNU gcc 16.

The method is thick-restart Lanczos with full reorthogonalisation over a pluggable operator, so shift-invert ('sm') and direct ('lm') share one code path. Because reorthogonalisation is full, the projected-matrix columns it computes are the thick-restart arrow structure — so the restart costs no extra bookkeeping at all.

Two bugs the measurements caught

Where writing the code changed the design

1 · A "safely tiny" shift cost 75× in solves

For a singular matrix I first set the regularising shift to δ = 10⁻¹⁰‖A‖, on the reasoning that smaller is safer. It is not. That makes θ₀/θ₁ ≈ 3×10⁷, which pollutes the small Ritz values enough that convergence never certifies: 3,020 solves and a partial-convergence flag, versus 40 solves at δ = 10⁻⁶‖A‖ for identical accuracy. The good region turned out to be broad — 10⁻⁶ to 10⁻³ at both n = 4,096 and n = 13,824 — so the default is now its conservative end. My test had not asserted the convergence flag, so the bad default passed silently; it does now.

2 · Raising that default made the solver answer the wrong question

With a larger starting δ, the escalation loop for a genuinely indefinite matrix could reach δ ≈ 18 and succeed at Cholesky — but shift-invert at δ = 18 converges to the eigenvalues nearest −18, not those nearest zero. It returned a confident, wrong answer. The fix is a hard cap: for a positive semi-definite matrix the very first shift always works, so needing a large one is proof the matrix is indefinite and must go to LU instead. The escalation now stops at 10⁻³‖A‖.

Honest limits

What this does not do

1 · It misses the requirement below n ≈ 58,000

3.6–3.9× on the sizes I tested below the crossover. This is the headline caveat and it is structural, not a tuning failure. If his matrices are in the tens of thousands rather than the hundreds of thousands, the 5× requirement is not met as things stand.

2 · Still no end-to-end eigs comparison

Every number here compares against the cost eigs demonstrably pays — UMFPACK LU plus the same count of triangular solves — measured in the same process. It is not eigs itself, because there is no MATLAB on this machine. The MEX gateway compiles clean against both API eras but has never been run.

3 · One matrix family

All measurements are on 3-D Laplacians. They are a fair, well-understood proxy with realistic fill, and their known spectra are what make the validation rigorous — but they are one family. Irregular FEM meshes, circuit matrices and graph Laplacians will each behave differently, and some will favour this approach more than the Laplacian does.

4 · Not yet implemented

Connected-component splitting and the banded path are designed and documented but not written; the structure pass currently detects the diagonal case and dispatches to dense LAPACK for small n. Complex Hermitian input is rejected with a clear error rather than silently mishandled.

Open questions

What I still need to close this out

  • Operating system and processor architecture, plus the exact MATLAB version. This is blocking. R2017a is Intel-only and expects Xcode ≈ 8; this machine is Apple Silicon on macOS 26 with clang 17, so the MEX file almost certainly has to be compiled on the target machine, against a statically linked SuiteSparse built for that architecture.
  • Typical n and nnz, and typical k. These set the dense/sparse threshold, the AMD/METIS threshold, and whether the exercise is worth doing at all.
  • Are the matrices ever complex Hermitian, or always real symmetric? It doubles the kernel count, and is much cheaper to know now than to retrofit.
  • A representative matrix or two. Far more informative than any synthetic test. Everything above is measured on a 3-D Laplacian, which is a reasonable proxy but is not the actual problem.
Method

How the 5× claim will be defended

A performance claim put to a referee has to survive scrutiny, so the benchmark protocol is fixed in advance:

  • Match accuracy, not tolerance. Compare at equal achieved residual ‖Av − λv‖ / (‖A‖‖v‖) against the original A, and report residuals for both codes. A faster wrong answer is not faster.
  • Verify the same eigenvalues were found, as a set, to tolerance — this catches "converged quickly to the wrong end of the spectrum".
  • Report thread counts, and give single-threaded numbers too, so the result cannot be dismissed as having simply used more cores.
  • Use real matrices from the SuiteSparse Matrix Collection, not sprandsym. Random sparse matrices have no exploitable structure, are unrepresentative of applications, and would in fact flatter mine on fill.
  • Report per-matrix results, the geometric mean, and the worst case. Publishing only the mean is how benchmarks lose credibility.
