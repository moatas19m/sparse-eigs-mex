The opening

Why there is room to win at all

eigs is not slow because it is written in MATLAB — underneath it is ARPACK, compiled Fortran. It is slow here because of three specific decisions, each of which I can reverse.

For the smallest-magnitude case it performs a shift-invert: factorize A, then run Lanczos on A⁻¹. To factorize, it calls MATLAB's lu — which is UMFPACK unsymmetric multifrontal LU, even when the matrix is symmetric positive definite. It orders with AMD rather than nested dissection. And on R2017a and older, ARPACK's reverse-communication interface hands control back to the MATLAB interpreter once per matrix-vector product.

So eigs throws away symmetry, throws away positive-definiteness, uses a weaker ordering for three-dimensional problems, and pays an interpreter round trip on every iteration. It also never inspects the sparsity pattern for reducibility, disconnection, or bandedness.

Evidence

What the two factorization paths actually cost

I wrote a standalone probe timing both paths on the same matrix: a 3-D 7-point Laplacian, which produces realistic finite-element fill. Not a benchmark of eigs itself — a measurement of the component that dominates its runtime.

The flop ratio of about 4× is roughly half from exploiting symmetry and half from METIS nested dissection beating AMD on a 3-D problem. The remaining wall-clock gain is supernodal BLAS-3 efficiency: CHOLMOD assembles large dense supernodes that Accelerate can drive at near-peak rate, where UMFPACK's frontal matrices are smaller and less efficient.

A correction to my own first measurement

My initial probe reported a fill ratio of 39× and a flop ratio of 173×. Those were wrong — I had read UMFPACK's *_ESTIMATE fields, which are symbolic upper bounds, against CHOLMOD's actuals. Reading the post-factorization actuals gives the honest 2.87× and 4.03× above. The timings were measured directly and were never affected. Worth stating plainly, because an unchallenged 173× would not have survived contact with a referee.

The argument

Why the advantage grows with difficulty

Shift-invert pays for one factorization and then one triangular solve per Lanczos iteration. Because my per-solve advantage (9.0×) is larger than my factorization advantage (3.8×), the end-to-end speedup rises with iteration count. Hard problems — clustered spectra, larger k, tighter tolerances — favour mine.

Modelled end-to-end speedup versus number of triangular solves, from the measured factorization and solve times above (n = 64,000, k = 6). Horizontal axis is logarithmic in solve count. The 5× requirement is met from roughly 17 iterations onward; typical shift-invert Lanczos runs use 40–300.

The semi-definite case

Where eigs is not just slower — it is wrong

The requirement notes that the matrices may be only semi-definite. That is the sharpest part of the requirement: if A is singular, shift-inverting at σ = 0 asks the code to invert a singular matrix. I probed it directly on a Neumann Laplacian — row sums zero, so it is positive semi-definite with rank n−1 and a one-dimensional null space.

n = 27,000, rank 26,999

cholmod_l_factorize  →  status = CHOLMOD_NOT_POSDEF,  L->minor = 26999 of 27000
umfpack_dl_numeric   →  status = UMFPACK_OK,           rcond   = 9.075e-13

CHOLMOD detects the rank deficiency exactly

It reports the precise column at which factorization broke down — L->minor = 26999, exactly the one-dimensional null space. That is a free, reliable rank signal I can act on.

UMFPACK reports success on a singular matrix

It returns OK with a reciprocal condition estimate of 9 × 10⁻¹³. This is the path eigs takes — it proceeds on a numerically meaningless factorization. So on semi-definite input, the proposed function is not merely faster; it is more correct. That may matter more to you than the timing.

How I handle it

Estimate ‖A‖₁, then factorize A + δI with δ escalating geometrically from ‖A‖₁·√ε. The probe confirms this succeeds at every δ tested, down to 1.2 × 10⁻¹¹. Run Lanczos on (A+δI)⁻¹ — then discard the shifted eigenvalue estimates entirely and recompute each λ as a Rayleigh quotient vᵀAv / vᵀv against the original A, reporting residuals ‖Av − λv‖ against the original A as well.

The consequence is the point: δ affects only the rate of convergence, never the accuracy of the answer.

One further trap. A semi-definite matrix has λ = 0 with multiplicity equal to its nullity, and plain Lanczos is notorious for missing repeated eigenvalues. I therefore use block Lanczos with full reorthogonalisation and explicit locking. That is a correctness requirement here, not an optimisation — and the block structure happens to convert the triangular solves from BLAS-2 to BLAS-3, so it pays for itself in speed too.

Your second requirement

Exploiting the nonzero structure

Every test below is O(nnz) and runs before any numerical work. eigs performs none of them. These are where order-of-magnitude wins live, as opposed to the steady 5–8× from the factorization.

For a general non-symmetric matrix the analogous win is block-triangularisation by Tarjan strongly-connected components, where the spectrum is the union of the diagonal blocks' spectra. Not needed for SPD, but it is how the design keeps the "works for any matrix" promise if the symmetry assumption is ever relaxed.

A decision made from data, not taste

Which ordering, and when

METIS nested dissection is not universally better. At n = 64,000 it costs about 0.45 s more in symbolic analysis than AMD, but saves 0.22 s per factorization and 7.4 ms per solve. Break-even is around 30 solves. Since shift-invert Lanczos performs 40–300, METIS wins for large problems — but at n = 4,096 its analysis cost alone dominates the entire solve.

Hence the rule: AMD below roughly n = 20,000, METIS above. The threshold is derived from the measurements, and will be re-tuned on the target matrices once they are available.

Honest limits

Three places this could fall short

1 · Small matrices

At n = 4,096 the measured factorization-plus-solve advantage is only about 3.5×. There I must clear the bar through the dense LAPACK fallback and by eliminating eigs' per-iteration interpreter overhead — not through the factorization. On a specific small matrix I may land at 3–4× rather than 5×.

2 · Problems that are already fast

If the matrices in real use are solved in under a tenth of a second, a 5× speedup is academic. Worth confirming the sizes actually in play before investing further — this is the question whose answer most affects whether the work is worth doing.

3 · These are component measurements plus a model

They are not an end-to-end eigs benchmark, because there is no MATLAB installation on this machine. The factorization and solve timings are real and directly measured; the 6.0–8.2× figure is those timings composed through the shift-invert iteration count. The real benchmark is the next step, and it needs a machine with MATLAB.

Before any code is written

What is still needed

  • Operating system and processor architecture, plus the exact MATLAB version. This is blocking. R2017a is Intel-only and expects Xcode ≈ 8; this machine is Apple Silicon on macOS 26 with clang 17, so the MEX file almost certainly has to be compiled on the target machine, against a statically linked SuiteSparse built for that architecture.
  • Typical n and nnz, and typical k. These set the dense/sparse threshold, the AMD/METIS threshold, and whether the exercise is worth doing at all.
  • Are the matrices ever complex Hermitian, or always real symmetric? It doubles the kernel count, and is much cheaper to know now than to retrofit.
  • A representative matrix or two. Far more informative than any synthetic test. Everything above is measured on a 3-D Laplacian, which is a reasonable proxy but is not the actual problem.
Method

How the 5× claim will be defended

A performance claim put to a referee has to survive scrutiny, so the benchmark protocol is fixed in advance:

  • Match accuracy, not tolerance. Compare at equal achieved residual ‖Av − λv‖ / (‖A‖‖v‖) against the original A, and report residuals for both codes. A faster wrong answer is not faster.
  • Verify the same eigenvalues were found, as a set, to tolerance — this catches "converged quickly to the wrong end of the spectrum".
  • Report thread counts, and give single-threaded numbers too, so the result cannot be dismissed as having simply used more cores.
  • Use real matrices from the SuiteSparse Matrix Collection, not sprandsym. Random sparse matrices have no exploitable structure, are unrepresentative of applications, and would in fact flatter mine on fill.
  • Report per-matrix results, the geometric mean, and the worst case. Publishing only the mean is how benchmarks lose credibility.
